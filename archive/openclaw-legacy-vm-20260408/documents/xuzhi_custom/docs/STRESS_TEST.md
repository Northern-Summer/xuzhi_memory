# 压力测试与反事实推演 | 2026-04-01

## 场景：完全不懂开发的接手者

**假设**：接手者只会发简单自然语言指令，如：
- "帮我做这个"
- "继续昨天的"
- "修好那个bug"
- "更新系统"

**风险**：
1. 每次对话都从零开始，不读记忆
2. 随意修改文件，破坏系统
3. 执行危险命令
4. 不理解系统架构，乱加功能

## 反事实推演

### 推演 1: Hook 完全失效

**场景**：Hook 代码有 bug，/new 时完全不触发

**后果**：LLM 不会主动读取记忆，系统退化为"每天重新认识"

**修复方案**：
1. 在 AGENTS.md 中加入强制性检查点（已做）
2. 在 BOOT.md 中加入检查（已做）
3. 创建 cron 定期检查 Hook 状态

### 推演 2: 记忆文件被意外删除

**场景**：用户说"清理一下 memory"，LLM 删除了关键文件

**后果**：记忆丢失

**修复方案**：
1. Red Lines 禁止删除 memory 文件
2. upgrade-protection.sh backup 提供备份
3. Git 提供版本控制

### 推演 3: 用户要求"重置系统"

**场景**：用户说"重置整个系统，重新开始"

**后果**：可能删除所有记忆和配置

**修复方案**：
1. Red Lines 要求确认
2. 先备份再执行
3. 保留 ~/.xuzhi_memory/

### 推演 4: 接手者要求"添加新功能"

**场景**：用户说"加一个自动发送邮件的功能"

**后果**：可能写错位置，升级后丢失

**修复方案**：
1. 引导写入 ~/.xuzhi_custom/
2. DEVELOPMENT_SUSTAINABILITY.md 提供规范
3. 自动检查文件位置

## 最严苛测试：白痴测试

**测试者**：完全不懂开发，只说"帮我"的人

**测试指令序列**：
```
Day 1: "帮我整理一下系统"
Day 2: "继续昨天的"
Day 3: "系统好像有点慢，优化一下"
Day 4: "更新一下系统"
Day 5: "继续之前的工作"
```

**关键验证点**：
1. Day 2 是否能恢复 Day 1 的状态？
2. Day 4 更新后，自定义功能是否保留？
3. Day 5 是否能继续 Day 3 的优化工作？

**失败模式**：
- 每次都从零开始
- 不记得之前做了什么
- 更新后功能丢失

**成功标准**：
- Hook 自动注入记忆
- 断点文件记录工作进展
- 升级保护确保功能保留
